### 2.3 工时算法（核心，必须正确）

采用**区间交集法**，严格满足"按工作区间算、午休排除"：

```
工作日总工时 = Σ 与标准区间交集(正常) + 早于08:00(额外) + 晚于18:00(加班)
周末总工时 = 下工 − 上工（不扣午休，全部计周末加班）
EXP = 总分钟 ÷ 6    （即 60 分钟 = 10 EXP）
等级 = floor(累计EXP ÷ 100) + 1
```

**EXP 精度（V-ming 2026-10-02 要求）：所有 EXP 计算保留 1 位小数，采用四舍五入。**
实现：`expFromMinutes = round1(minutes/6)`，`round1(x)=Math.round(x*10)/10`（标准四舍五入，0.5 进位）。
- 场景 A 08–18 → 480min → **80.0 EXP**
- 场景 B 08–20 → 600min → **100.0 EXP**（加班 2h）
- 场景 C 07:30–18:30 → 540min → **90.0 EXP**（你已确认此口径）
- 场景 D 周六 09–13 → 240min → **40.0 EXP**
- 非整分钟示例：483min → **80.5 EXP**；61min → **10.2 EXP**

## 三、🔧 验收未通过的 BUG 排查与修复（本次重新提交核心）

### 3.1 现象（你反馈的）
`npm start` 后阿七小黑猫出现，但：**拖动失效、点击阿七弹卡失效**；托盘右键「上工/下工」点击**无反应**。因此无法继续验收。

### 3.2 根因（单一原因，串联三处现象）
`main.js` 在 `createWindow()` 与 `showWindow()` 中调用了：

```js
mainWindow.setIgnoreMouseEvents(true, { forward: true });
```

该 API 的含义是**整窗忽略鼠标事件、全部转发给桌面背后的窗口**。后果是阿七的 DOM 元素（`#pet`）**根本收不到 `mouseenter`/`mousedown`/`mouseup`**：
- 拖动失效（收不到 mousedown/mousemove）
- 点击弹卡失效（收不到 mouseup → `toggleCard` 不触发）
- 托盘「上工/下工」逻辑本身没坏（集成测试 13/13 通过），但点击后只改了数据、**卡片始终隐藏、窗口又被设成穿透态 → 没有任何可见反馈**，表现为"无反应"

### 3.3 修复
1. **移除整窗穿透**：不再对窗口 `setIgnoreMouseEvents(true)`。窗口恢复可交互。
2. **改用 CSS 命中控制**：`body` 设 `pointer-events:none`（透明区不拦截），仅 `.pet` 与 `.card` 设 `pointer-events:auto`（阿七本体与卡片可点）。拖动/点击现在能正常命中阿七本体。
3. **移除已失效的 hover 切交互代码**：`app.js` 中原先靠 `mouseenter` 临时切回可交互的逻辑，正是依赖穿透、本就不会触发，已删除，避免误导。
4. **托盘点击给可见反馈**：上工/下工后主进程通过 `webContents.send('aqi:open-card')` 通知渲染层自动弹出卡片并刷新，使托盘操作可感知。
5. **EXP 一位小数**：按你要求落实为 `round1`，显示与存储统一 1 位小数。

### 3.4 一个需要你知晓的取舍（透明区点击穿透）
修复后**窗口可交互、阿七可拖动可点击**；但代价是：窗口 180×200 的矩形边框内、阿七本体之外的**透明留白区会"吃掉"点击**（不会穿透到桌面）。这是 Electron 透明窗口"既要整窗穿透、又要局部可交互"的固有矛盾——两者无法同时用原生 API 完美兼顾。

- 阿七本体 150×150 可正常交互；四周约 15~25px 的透明边会拦截点击（不穿透到桌面）。
- 对桌面陪伴型小宠，影响很小，多数开源桌宠也如此实现。
- **如果你坚持要"透明区真正穿透到桌面"**，我有两条后续可行路线（不阻塞本次验收，需单独排期）：
  - a) 缩小窗口到几乎贴合阿七本体，最小化拦截区；
  - b) 进阶方案：用一处轻量光标邻近检测在"贴近阿七"时切回可交互、远离时整窗穿透（需少量主进程轮询，复杂度更高）。

## 十、第四次复查（PM 反馈"可拖动、但单击无反应、托盘点击无反应"）

> 上一版（第九节）把拖拽改成 `-webkit-app-region: drag`，结果 PM 实测：**拖动可用，但单击弹卡失效、托盘点击也看不到反馈**。这说明第九节的"原生拖拽区"方案本身有缺陷，需再次修正。

### 10.1 真正的根因（两处，已分别验证）

1. **`.pet` 上的 `-webkit-app-region: drag` 会吃掉 `mouseup`/`click`。**
   这是 Electron/Chromium 的已知行为：被标记为"拖拽区"的元素，按下后由 OS 窗口管理器接管拖动，**不会向页面派发 `mouseup` 与 `click` 事件**。所以系统拖拽能用（"可拖动"通过），但 `app.js` 里靠 `mouseup` 判别"单击→弹卡"的监听永远收不到事件——卡片打不开。
2. **托盘点击其实有执行，但缺少可见反馈。**
   托盘「上工/下工」的 `click` 回调确实跑了 `punchIn/punchOut` 并 `webContents.send('aqi:open-card')`，但 `showWindow()` 只 `show()` 不 `focus()`，小卡片又半透明、易被忽略，于是 PM 看到"无反应"。

### 10.2 本轮修复（彻底弃用拖拽区，回退到 JS 拖动 + 强制反馈）

| 改动 | 文件 | 目的 |

### 11.2 本轮定位到的**两处真实代码缺陷**

1. **拖动坐标系用错**：`mousemove` 里用 `e.clientX`（相对窗口）算位移。窗口一被移动，参照系就变，位移必然算错；且"是否拖动过"用 `Math.abs(clientX-downX)>3` 判定——窗口跟随光标后该差值恒为 0，判定失灵。
   → **改用 `screenX/screenY`（屏幕绝对坐标）**，位移才准确。
2. **点击/拖动判别太脆**：3px 阈值 + 手抖即被当成拖动 → 很多"单击"被误判为拖动，卡片弹不出来。

## 十二、第六次修复（根因确证：标识符冲突导致整份脚本不执行）

> V-ming 提供 `diag.log` 后，根因**一锤定音**。这也是你一直怀疑的"代码冲突"——确实是。

### 12.1 诊断日志给出的铁证

```
[main] app ready
[main] createWindow
[main] tray created
[renderer-console] Uncaught SyntaxError: Identifier 'aqi' has already been declared  <file:///.../src/app.js>
[main] did-finish-load
[tray] 上工 ok=true
```

### 12.2 根因与机理

- `preload.js` 用 `contextBridge.exposeInMainWorld('aqi', …)` 注入的全局 `aqi`，是一个**不可配置（non-configurable）**属性。
- `app.js` 顶层写了 `const aqi = window.aqi`。按 JS 规范，全局词法声明在实例化时会做「受限全局属性」检查：若全局对象上已存在**不可配置**的同名属性，则抛
  `SyntaxError: Identifier 'aqi' has already been declared`。
- **语法错误会让整份脚本直接不执行**（不是运行时报错，`try/catch` 也拦不住）。于是：拖动监听、点击弹卡、托盘 `onOpenCard` 全部没注册 → 拖不动、点不出卡、托盘无反应。
- **黑猫仍显示**：它是 `styles.css` + SVG 画的，不依赖 JS，所以极具迷惑性。

### 12.3 为什么"阶段一好、阶段二坏"（你的判断完全正确）

- **阶段一**的 `app.js` 直接使用 `window.aqi.*`，**没有** `const aqi` 这句，所以脚本正常执行，拖动/点击验收通过。
- **阶段二**我为了写得干净，引入了 `const aqi = window.aqi`——正是这句把整份脚本废掉了。**属于我引入的回归。**

### 12.4 为什么前几轮的"语法检查"没抓到

`node --check` 只对**单个文件**做语法解析，**不模拟**"全局作用域里已存在同名不可配置属性"这种跨文件/宿主环境场景，所以它一路绿灯。这是检查手段的盲区，不是笔误。
