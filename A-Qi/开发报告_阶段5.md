## 二、关键设计决策

### 2.1 职责分离：TXT 是记录，tasks.json 是状态（技术规格 §28）

- **【明日待办】的内容永远由你手写**，程序只**读**不改；
- 勾选状态只写入 `data/tasks.json`：

```json
{
  "2026-10-04": [
    { "text": "继续完成南安项目", "completed": false },
    { "text": "找结构专业要条件。", "completed": false }
  ]
}
```

- 状态按**文本匹配**合并回条目（若你改了某条的文字，该条视为未完成 —— 安全优先，不会错勾）。

### 2.2 「空列表不落盘」—— 允许你事后补写

首次打开「今日待办」时，若前一天的工作记录还没有内容，程序**不会把"空"缓存下来**。
所以你早上打开看到空的 → 去补写昨天的【明日待办】→ 再打开就能看到，**不需要重启程序**。

### 2.3 统计口径（6 条，**请你确认**）

| # | 口径 | 说明 |
|---|---|---|
| 1 | **只统计「已完成」记录** | `working` / `incomplete`（忘记下工）/ `absent`（这天没上班）**一律不计入任何统计** |
| 2 | **本周 = 周一起算** | 周一 ~ 今天（中国习惯），不是周日 |
| 3 | **本月 = 当月 1 日 ~ 今天** | |
| 4 | **工作天数 = 该时段有出勤记录的天数（含周末加班日）** | 这样才与「总工作时长」「平均每日」口径自洽；工作日/周末的拆分由两行「加班次数」体现 |
| 5 | **平均每日工作时长 = 总工作时长 ÷ 工作天数** | 无记录时为 0 |
| 6 | **连续工作 = 从今天（若今天已下工）或昨天向前回溯，连续有完成记录的天数；任何一天（含周六/周日）没有完成记录即中断** | 例：三/二/一有记录、周日空、周六有记录 → **连续 3 天**；日/一/二/三有记录、周六空 → **连续 4 天** |

> 第 4、6 条是为口径自洽所做的定义（规格只列了指标名）。两条**均已由 PM 确认**：第 4 条认可；
> 第 6 条经 PM 在 2026-10-05 修订为「**周末无记录同样中断**」——原实现是"周末跳过不中断"，
> 已按 PM 新口径改正（见第九节）。

### 2.4 UI 形态

- 仍是**普通窗口**（系统标题栏 + 原生关闭按钮），沿用阶段 4 你已确认的形态；
- **一个窗口上下两区**（不是两个窗口）：上半「📋 今日待办」、下半「📊 工作统计」，一屏看全，无需页签切换；
- 托盘新增两个入口都打开同一窗口，只是**滚动定位**到对应区域，并在打开时**自动刷新**数据（所以刚下工完再打开，统计是最新的）。

### 2.5 一个我自己踩的坑（已修，记录备查）

新增**纯逻辑模块**和**窗口脚本**时我一度都用 `src/todo.js`，后者把前者覆盖了，导致主进程 `require('./src/todo')` 时报 `window is not defined`。
现已拆分为：**`src/todo.js` = 纯逻辑（被主进程 require）**、**`src/todo-window.js` = 窗口脚本（被 todo.html 加载）**，并加了测试断言防止再次写错文件名。
